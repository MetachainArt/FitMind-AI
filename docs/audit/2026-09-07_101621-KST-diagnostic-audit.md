| 식단 안내·영상 링크 | 정적 안내/운동별 검색 URL | 문구와 링크 구성 확인. 링크는 YouTube 검색이며 검증된 특정 운동 영상 보증 기능은 아님 |

AI라고 표시하는 샘플 응답, 유료 모델 호출, OAuth 우회 경로는 발견하지 않았다. 기본 루틴·식단 템플릿은 이 개인 앱의 의도된 데이터이며 하드코딩이라는 이유만으로 오류로 분류하지 않았다.

### BUG-001 — 실패한 복원 이후에도 저장소는 교체된 상태

- 분류/영향: BUG, P1. 불완전하거나 손상된 백업을 선택한 사용자는 실패 안내를 보지만 기존 영구 기록이 이미 교체된다. 모든 정상 백업이 실패하는 문제는 아니며 P0로 확대하지 않는다.
- 근거: `app.js:1863` importAppData, 특히 1887–1899; `normalizeLoadedState` 3248–3256; `renderGeneratedPlanResult` 1938, 1959.
- 재현: 기존 history가 있는 메모리 저장소 준비 → `{ "sessions": {}, "generatedPlanDraft": {} }` JSON 복원 승인 → 결과 렌더링 → 재로드.
- 기대/실제: 유효하지 않은 백업은 기존 데이터를 보존하고 거절해야 한다. 실제로 persistState가 렌더링보다 먼저 실행되고, schedule.map 예외 후 catch는 메모리만 되돌린다.
- 실행 증거: 실패 메시지, `memoryDraft:null`, `diskDraft:{}`, `diskHistory:0`. 재로드 시 `Cannot read properties of undefined (reading 'map')`. VM에서는 렌더링을 해당 실제 함수 호출로 한정했으며 브라우저 파일 업로드 재현은 미실행이다.
- 최소 수정: 중첩 스키마 검증을 저장 전에 수행하고, 준비/검증 성공 후에 교체한다. 교체 실패의 디스크·메모리·타이머 복구를 일관되게 처리한다.
- 영향/완료 테스트: 백업 호환성·생성 계획·타이머. 정상/구버전/누락 schedule·meal/용량 초과/취소 복원 후 기존 저장 JSON 및 새로고침 결과 보존 검증.

### BUG-002 — 오늘 기록 초기화가 예외로 중단

- 분류/영향: BUG, P1. 제공되는 초기화 흐름이 멈추고 현재 세션이 메모리에서 사라져 이후 조작도 실패할 수 있다.
- 근거: `app.js:696–713` 초기화 이벤트; `pauseWorkoutTimer` 2629–2640. 702에서 세션을 지운 뒤 704에서 그 세션을 다시 사용한다.
- 재현: 한 세트 수행 → ‘오늘 기록 초기화’ → 확인. 최초 빈 세션에서도 같은 코드 순서다.
- 기대/실제: 타이머 종료와 기록 재생성 후 0세트. 실제 화면에는 이전 `1/17`이 남고 콘솔 `Cannot set properties of undefined (setting 'workoutTimerRunning')`, `app.js:2637`, 호출 `704` 확인.
- 검증: 브라우저와 VM 재현. 자동화 클릭은 확인창 처리 중 타임아웃을 반환했지만 앱 콘솔 예외와 VM 동일 실패로 제품 오류를 별도 확인했다.
- 최소 수정: 존재하는 세션에서 타이머를 먼저 정리한 뒤 삭제·재생성·저장. 초기화 시 기존 history를 함께 지울지는 제품 의미를 확정해야 한다.
- 영향/완료 테스트: 세션·타이머·요약. 실행 중/일시정지/빈 세션 초기화, 확인 취소, 실패 후 조작, 새로고침 후 0 상태 확인.

### BUG-003 — 결측 인바디 지표를 실측 0으로 취급

- 분류/영향: BUG, P1. 기록의 의미와 조정 결과를 바꾼다. 의료적 유해성을 추정한 분류가 아니라 실제 미입력 데이터를 측정값으로 만드는 오류다.
- 근거: `saveInbodyRecord` 1633–1637, `normalizeInbodyRecord` 1765–1769, `normalizeOptionalNumber` 1807–1809, `hasCoreInbodyMetrics` 1743–1747.
- 재현: 체중 70만 입력, 다른 지표 공란 → 저장.
- 기대/실제: 미입력 지표는 빈 값 유지 및 추가 입력 안내. 실제 `골격근량 0kg | 체지방률 0% | 내장지방 0레벨 | 허리 0cm` 표시와 ‘골격근량을 더 올려야 합니다’ 출력.
- 증거/검증: 브라우저·VM 실행 재현. `readOptionalNumber`의 null이 정규화 중 `Number(null) === 0`으로 바뀐다.
- 최소 수정: null/undefined/빈 문자열을 먼저 구분하고 유효 수치만 비교한다. 기존 0을 모두 결측으로 바꾸는 일괄 데이터 수정은 피하고 복구 기준을 따로 정한다.
- 영향/완료 테스트: 저장·조회·복원·조정안. 이미지 단독, 체중 단독, 모든 유효 수치, 실제 0/잘못된 입력의 구분을 저장·재로드 왕복으로 확인.

### BUG-004 — 3/4세트인데 이미 완료로 잠김

### BUG-005 — 이미지 제외 재시도에 이미지가 그대로 남음

- 분류/영향: BUG, P2. 공간 부족 때 제공하려던 수치만 저장하는 복구 경로가 작동하지 않는다.
- 근거: `saveInbodyRecord` 1655–1668, `trimInbodyRecords` 1776–1789, `normalizeInbodyRecord` 1761–1773.
- 재현: 테스트 이미지 문자열을 포함한 인바디 입력 → 이미지가 있으면 실패하고 없으면 성공하는 persistState 대역으로 실행.

- 검증: VM 실행 재현. trim 과정에서 복제한 뒤 원본 record만 비워 실제 state를 변경하지 못한다. 실제 디스크 공간 고갈은 유발하지 않았다.
- 최소 수정: 저장 후보 레코드의 이미지를 제거한 새 배열로 재시도하고 최종 실패 시 기존 상태를 보존한다.
- 영향/완료 테스트: 인바디 보관 한도·동일 날짜 교체·저장 오류. 이미지 실패→수치 성공, 두 번 실패, 기존 기록 보존을 검증.

### BUG-006 — 집·맨몸과 머신 추천이 모순

- 분류/영향: BUG, P2. 생성된 계획을 입력한 환경에서 수행할 수 없고 등 요일 구성도 목표 부위와 어긋난다.
- 근거: `DEFAULT_GENERATOR_TEMPLATES` 113–118, `selectGeneratedExercises` 2118–2146, 특히 장비 필터가 비면 조건을 완화하는 2140.
- 재현: 근육증가, 월/수/금, 70분, 초보, 집, 장비 ‘맨몸’, 유효 신체 입력 → 생성.
- 기대/실제: 맨몸 운동 또는 후보 부족 안내. 실제 레그프레스·힙쓰러스트 머신·체스트프레스 머신 추천. ‘등’ 요일에도 이 머신 운동과 플랭크류가 반환됨.
- 검증: 브라우저 및 기본 템플릿 VM 재현. 머신 이름 템플릿에 집·맨몸 허용 태그가 붙고 다른 부위 풀로 채우는 경로가 있다.

- 영향/완료 테스트: 생성기·관리자 템플릿. 집/야외/헬스장 × 장비 없음/밴드/특정 장비 × 부상 필터를 통과한 모든 결과의 조건 일치 확인.

### BUG-007 — 시간 예산을 넘기는 맞춤 생성

- 분류/영향: BUG, P2. 입력한 가능 시간 내에 계획을 마칠 수 없다.
- 근거: `selectGeneratedExercises` 2143–2156, `getIntensityByExperience` 2163–2170, `getCardioPlan/getCardioDuration` 2173–2191.
- 재현: 체중감량·월수금·15분·고급·헬스장으로 기본 템플릿 생성.
- 기대/실제: 총 시간이 15분에 맞아야 함. 실제 첫날 3종목×4세트·휴식90초와 유산소 8–12분. 각 종목 마지막 세트 후 휴식을 제외해도 `3 × 3 × 90초 = 13.5분`, 유산소 최소 8분을 더해 21.5분이다. 운동 수행·이동 시간은 이 계산에 포함하지도 않았다.

- 최소 수정: 준비·세트·휴식·유산소를 공유 시간 예산에 배정하고 부족하면 세트/운동 수를 줄이거나 설명한다.
- 영향/완료 테스트: 목표·경험·유산소 조합. 15/30/70/180분에서 생성 예산 합계가 입력시간을 넘지 않는지 검증.

### BUG-008 — 6개월 변화를 4주 속도로 표현

### BUG-009 — 자정 이후 세션 키와 요약 날짜가 다름

- 분류/영향: BUG, P2. 앱을 자정 넘어 열어 둔 경우 과거 세션의 요약이 다음날 집계로 이동할 수 있다.

- 재현: 날짜 함수 대역을 2026-09-07로 설정해 월요일 세션 생성·1세트 입력 → 2026-09-08로 변경 → 요약 생성.
- 기대/실제: 정의된 세션 날짜 정책에 맞는 키/날짜. 실제 `sessionKey:2026-09-07_MON`, `date:2026-09-08`, `setDone:1`. 같은 키 upsert로 이전 날짜 요약을 덮을 수 있다.
- 검증: 날짜 대역 VM 재현. 실제 자정 대기 미실행.
- 최소 수정: 세션 시작일을 요약에 유지하거나 날짜 경계에서 안전하게 새 세션으로 전환하는 정책을 정하고 통일한다.
- 영향/완료 테스트: 통계·지속 타이머·요일 선택. 자정/월말/연말, 다음날 새로고침·요약 중복 저장 검증.

### BUG-010 — 완주와 운동 시간 종료가 연결되지 않음

- 분류/영향: BUG, P2. ‘완료’ 후에도 시간이 늘어나 저장된 요약과 화면 시간이 달라지고, 사용자가 나중에 수동 저장하면 운동 외 시간까지 기록된다.
- 근거: 세트/운동 완료 이벤트 `553–607`, `saveCurrentSummary` 1333–1358, `startWorkoutTimer` 2614–2626. 자동 요약 전에 종료 처리 없음.
- 재현: 모든 운동 완료 후 화면과 기록의 시간 비교.
- 기대/실제: 완료 시 일관된 종료 시간. 실제 자동 저장 `02:51`, 이후 화면 `03:04`이고 버튼은 ‘타이머 일시정지’. 사용자가 별도로 멈추자 정지했다.
- 검증: 브라우저 실행 재현. 조회한 두 시간은 테스트 세션에서 실제 관찰한 값이다.
- 최소 수정: 마지막 운동 완료 시 시간 확정·타이머 정지 후 요약 저장. 운동 완료 후 별도 시간을 재는 의도가 있다면 명시적인 분리 동작이 필요하다.
- 영향/완료 테스트: 자동/수동 요약, 마지막 세트·운동 완료 버튼, 새로고침. 완료 후 시간이 유지되고 화면·저장·재조회가 같은지 확인.

### BUG-011 — LocalStorage 읽기 예외 처리 누락

- 분류/영향: BUG, P2. 저장 접근이 거절되는 환경에서는 첫 실행이 멈추고 저장 제한 안내도 렌더링되지 않는다. 정상 브라우저 전체에서 발생하는 문제로 일반화하지 않는다.
- 근거: `loadState` 3275–3284. getItem이 try 바깥이며 전역 state 초기화 456에서 호출한다.
- 재현: localStorage.getItem이 SecurityError를 던지도록 메모리 대역 구성 → 원본 스크립트 초기 평가.
- 기대/실제: 제한 안내와 가능한 임시 사용/복구 경로. 실제 예외가 전역 실행을 중단한다.
- 검증: 오류 주입 VM 재현. 실제 브라우저 권한 설정을 바꾸지 않았다.
- 최소 수정: 저장소 접근 자체까지 예외 경계에 포함하고 읽기 실패·JSON 손상·공간 부족을 구분한다. 읽기 실패 뒤 초기값으로 기존 데이터를 덮어쓰지 않도록 주의한다.
- 영향/완료 테스트: bootstrap·persistState·백업. SecurityError/깨진 JSON/빈 저장소/정상 저장소 각각의 화면과 기존 데이터 보존 검증.

## 6. 추가 확인이 필요한 위험

### RISK-001 — 여러 탭의 전체 상태 덮어쓰기

- 분류/우선순위: RISK, P2. 전제는 같은 origin을 두 탭에서 동시에 편집하는 경우.
- 근거: `app.js:456` 탭별 상태 로드, `3287–3295` 전체 JSON 저장. storage 이벤트·리비전 충돌 처리 없음.
- 기대/예상 영향: 두 탭에서 기록한 서로 다른 변경이 함께 남아야 하지만 마지막 저장 탭의 오래된 전체 상태가 다른 기록을 덮을 수 있다. 실제 동시 탭 재현은 미실행.
- 추가 확인: 탭 A 인바디 저장 → 기존 상태의 탭 B 세트 완료 → 새 탭에서 두 기록 존재 확인. 타이머 주기 저장도 포함.
- 최소 방향/영향/완료 조건: 리비전 감지·외부 변경 안내 또는 안전 병합. 세션·이미지·생성 계획 모두 영향. 충돌을 조용히 덮지 않고 양쪽 변경 보존 또는 명시적 선택을 보장하는 테스트.

### RISK-002 — 백그라운드 휴식 타이머 정확도와 재시작

- 분류/우선순위: RISK, P2. 모바일 화면 잠금·백그라운드에서 interval 실행 간격이 지연되는 경우.
- 근거: `app.js:2536–2555`, `2571–2585`는 콜백마다 1초 감소. 운동 총시간의 timestamp 보정과 다르며 restTimer는 저장하지 않음.
- 기대/예상 영향: 실제 시간에 맞춰 휴식 종료를 안내해야 하나 지연 콜백 수에 따라 남은 시간이 부풀 수 있다. 새로고침 후 휴식은 사라지는 코드이며, 이를 복원해야 하는 제품 요구는 별도 확인 대상.
- 추가 확인: 실제 지원 기기에서 120초 타이머→잠금 60초→복귀, 정지/재개/새로고침 비교. 이번 검사에서는 장시간 실기기 검증 안 함.
- 최소 방향/영향/완료 조건: 종료 시각 기반 계산, 필요시 휴식 상태 복원. 세트 진행·건너뛰기에 영향. 실제 경과와 허용 오차 및 일시정지 의미를 테스트로 확정.

### RISK-003 — 개인화 입력과 건강 조정 규칙의 범위

- 분류/우선순위: RISK, P2. 일반 사용자에게도 같은 개인용 기준을 적용하는 경우의 제품 적합성 위험.
- 근거: `app.js:2038–2055` 키·나이·성별 필수 확인, 생성 결과 로직 2082–2232에는 이 세 필드에 따른 조정이 없음. 인바디 1723–1734는 허리·체지방·근육량 고정 경계로 안내.
- 기대/예상 영향: 사용자가 입력이 실제로 어떤 판단에 쓰이는지 이해해야 한다. 입력을 받는 것만으로 개인별 적합성이 검증되었다고 해석될 수 있다. 기준이 의학적으로 틀렸다고 확정한 항목은 아니다.
- 추가 확인: 의도한 대상이 작성자 개인인지 일반 대중인지 확인, 자격 있는 전문가에게 규칙·부상 태그·미성년 입력 허용 범위 검토 의뢰. 이번 작업은 임상 검토를 수행하지 않음.
- 최소 방향/영향/완료 조건: 사용하지 않는 필수 입력 완화 또는 용도 설명, 근거·적용 대상 명시. 인증 구조 변경이나 새 서비스 필요 없음. 동일 조건에서 어떤 입력이 결과를 바꾸는지 명시한 검증표 작성.

### RISK-004 — 전체 상태 동기 저장과 세션 무제한 누적

- 분류/우선순위: RISK, P2, 성능 개선 가설. 이미지를 포함한 상태가 커지거나 오래 사용하는 경우.
- 근거: `app.js:3289` 매번 전체 JSON stringify/setItem; `2653–2669` 운동 중 30초 단위 저장; `3159–3191` 세션 추가는 있지만 정리 한도 없음. `renderAll` 1064–1076은 세트 완료에도 생성기·인바디·편집 화면까지 다시 렌더링.
- 기대/예상 영향: 운동 버튼 응답이 유지되어야 하나 동기 직렬화·쓰기 및 불필요한 재렌더링이 지연/공간 부족을 키울 수 있다. 성능 병목으로 확정할 프로파일은 미수집.
- 추가 확인: 허용 이미지 6개와 1년/3년 가상 세션으로 버튼 처리·직렬화 시간과 저장 실패 지점을 프로파일링. 개선율이나 체감 지연 수치를 추정하지 않음.
- 최소 방향/영향/완료 조건: 먼저 측정, 관련 영역만 갱신, 보관 정책과 데이터별 저장 분리 검토. 세트·백업·마이그레이션에 영향. 기록 보존을 입증하면서 정한 응답 예산을 만족해야 함. 기존 데이터 자동 삭제는 별도 승인 대상.

보안 검토상 주요 동적 문자열은 escapeHtml 또는 textContent로 출력하며, 이미지 입력에는 형식·크기 및 압축 처리가 있다. 이것이 전체 보안 취약점 부재의 증명은 아니다. 명시적 코드 경로 없는 원격 공격·계정 탈취를 취약점으로 보고하지 않는다. 현재 중요한 데이터 무결성 문제는 BUG-001이다. 의존성은 없으며 최신이라는 이유의 라이브러리 일괄 교체 제안도 없다.

## 7. 기능 업그레이드 추천

아래는 사용자 수요가 아직 확인되지 않은 **제품 가설**이며 구현하지 않았다. 오류 수정과 별도다. 모두 기존 화면에 연결하는 작은 범위를 우선하며 신규 유료 서비스·프로덕션 라이브러리를 전제하지 않는다.

### IMP-001 — 생성 계획을 실제 운동 실행에 적용

- 분류: IMPROVEMENT, 추천 1순위. 생성 결과를 저장·보기만 할 수 있어 실행 루틴을 다시 편집해야 하는 한계.
- 제안/이점: 생성 결과의 요일·운동·세트를 변경 미리보기로 보여주고 선택 요일에 적용. 계획→세트 수행→요약으로 연결되어 중복 입력을 줄인다.
- 최소 범위/모듈: 생성 결과에 적용 버튼, 덮어쓸 요일/세트 미리보기, `generatedPlanDraft`, `customPlans`, `syncSessionToCurrentPlan` 연결. 기존 기본 루틴과 사용자 편집은 선택적으로 보존.
- 복잡도/위험: 중간. 생성 계획의 숫자 세트/반복 모델을 기존 문자열 세트 구조로 변환해야 하며 진행 중 세션 영향이 큼. BUG-004·006·007 수정 이후 착수 권장.
- 완료 조건: 적용한 계획으로 첫 세트 기록·자동 요약·새로고침 복원 성공, 미선택 요일 불변, 취소 시 기존 루틴 보존.
- 비용/승인: 새 외부 서비스 불필요. 현재는 진단만 승인되어 있어 구현은 후속 범위 승인 필요.

### IMP-002 — 실수로 누른 세트 완료의 되돌리기

- 분류: IMPROVEMENT, 추천 2순위. 세트 완료는 연속 클릭마다 늘지만 한 세트만 취소할 수 없어 전체 초기화에 의존하게 됨.
- 제안/이점: 마지막 완료 1회를 취소하고 세트·현재 운동·완료율을 일관되게 복원. 휴대폰에서 오입력을 적은 조작으로 수정.
- 최소 범위/모듈: `completeSetBtn` 처리와 세션 상태에 마지막 완료 동작 하나 보관, 현재 운동 영역에 되돌리기. 자동 요약도 동기화.
- 복잡도/위험: 중간. 운동 간 자동 이동과 이미 저장한 완주 요약에 영향. BUG-002·004·010 선행 권장.
- 완료 조건: 중간 세트/마지막 세트/최종 운동 취소 후 값 일치, 연속 클릭과 새로고침 정책 명확화.
- 비용/승인: 외부 비용·새 라이브러리 없음. 구현은 후속 요청 필요.

### IMP-003 — 계획이 입력 조건을 충족하는지 결과에서 설명

- 분류: IMPROVEMENT, 추천 3순위. 사용자는 생성 결과가 장비·시간·부상 제외 조건을 어떻게 반영했는지 확인하기 어렵다.
- 제안/이점: 예상 총시간, 필요한 장비, 부족한 부위 후보와 제외 이유를 결과에 함께 표시해 실행 전에 판단할 수 있게 한다.
- 최소 범위/모듈: `selectGeneratedExercises`, `getCardioPlan`, `renderGeneratedPlanResult`에 선택 근거/제약 충족 상태 추가. 새 메뉴 없음.
- 복잡도/위험: 중간. 기존 백업 계획 스키마에 선택 필드를 더하므로 과거 결과의 기본 표시 필요. BUG-001·006·007 이후 진행.
- 완료 조건: 불가능한 조건을 충족했다고 표시하지 않음, 후보 부족 안내, 시간 합계가 실제 생성 세트와 일치, 과거 백업도 열림.
- 비용/승인: 기존 계산과 UI로 가능. 의료 효과 보증 기능으로 확대하지 않으며 구현은 후속 요청 필요.

## 8. 가장 먼저 처리할 작업 — 최대 3개

1. **BUG-001 백업 복원 검증·교체 순서 수정**: 실패가 기존 영구 데이터를 교체할 수 있어 먼저 보호해야 한다. 손상 백업 회귀 검사를 함께 마련한다.
2. **BUG-002 기록 초기화 순서 수정**: 현재 제공하는 복구 동작 자체가 예외로 중단된다. 작은 범위에서 명확한 정상 흐름을 회복할 수 있다.
3. **BUG-003 결측값 보존 수정**: 사용자가 입력하지 않은 수치를 실측 0으로 저장하고 잘못된 조정안을 만드는 직접적인 데이터 오류다.

그다음 BUG-004·005와 생성기 BUG-006·007을 처리하는 순서를 권장한다. UI 꾸미기나 대규모 파일 분해보다 데이터 정확성과 기존 흐름 복구가 우선이다.

## 9. 수정 전 필요한 준비와 승인 사항

- 현재 요청은 진단만이므로 **프로그램 코드와 기능은 아직 수정하지 않았다**. 수정에 착수하려면 위 ID 중 후속 구현 범위를 지정받아야 한다. 이번 보고서 작성에는 추가 승인이 필요하지 않았다.
- 다음 작업 시작 시 Git 변경 상태를 다시 확인한다. 사용자의 현재 데이터와 문제 백업은 원본 보존·가상 복사본 테스트가 우선이며 실제 기록 삭제/교정은 별도 승인 대상이다.
- 버그 수정에 새 프로덕션 의존성은 현재 필요해 보이지 않는다. 필요해질 경우 기존 수단의 한계를 설명하고 승인받는다.
- 저장 구조 변경이 필요하면 구버전 백업 스키마와 결측/0 값 처리 정책을 먼저 정의한다. 특히 기존 0 측정값의 의미를 임의로 추정해 일괄 변경하지 않는다.
- 커밋·푸시·병합·배포·운영 데이터 변경·외부 발송·유료 서비스 호출은 실행하지 않았다. 향후에도 별도 승인 범위다.
- 운영 헤더 확인은 배포 주소가 확인되면 읽기 전용 검증 가능하다. 현재에는 인증/AI 실서비스 호출 자체가 없어 그 연결 검증 승인을 요청할 대상도 없다.
