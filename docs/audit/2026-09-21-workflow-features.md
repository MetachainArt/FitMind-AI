# 2026-09-21 추천·운동·기록 연결 기능

기존 루틴·기록·OAuth 연결을 유지하면서 요청된 5개 기능을 추가했다. 새 프로덕션 패키지는 설치하지 않았다. 원래 진단 보고서는 당시 상태의 기록으로 보존한다.

## 구현 및 사용 방법

| 기능 | 사용 방법 | 보존 정책과 한계 |
| --- | --- | --- |
| 1. 추천 계획을 실제 루틴에 적용 | 생성하거나 저장 목록에서 연 계획 → 적용할 요일 선택 → 변경 내용 미리보기 → 확인한 루틴 적용 | 선택한 요일만 변경한다. 진행 중이거나 오늘만 대체한 세션은 당일 `planSnapshot`을 유지한다. 최근 적용 1회 복원만 지원하며 적용 후 수동 편집한 루틴은 자동 복원하지 않는다. |
| 2. 실제 세트 기록·지난 기록 비교 | 실제 중량/맨몸·횟수/시간·선택 RIR 입력 → 세트 완료 또는 실제 기록 저장. 이전 값 불러오기 및 지난 기록 표의 수정·삭제 사용 | 목표 문자열과 실제 수행값을 분리한다. 기록만 저장할 때 완료 수는 변하지 않는다. 운동 ID가 바뀌어도 저장 당시 이름으로 비교한다. 자유문자·시간·맨몸 값을 보존하며 다른 단위를 임의로 합산하지 않는다. |
| 3. 여러 인바디 비교 | 인바디 비교 목록에서 0~6개 선택 → 수치별 측정 날짜·간격·변화량과 전송 미리보기 확인 | 체중 입력 기준 선택과 AI 전송 비교 목록은 별개다. 수치별 서로 다른 날짜의 유효값 2개 이상이 있어야 비교한다. 중복 선택된 측정 날짜는 변화량 계산에서 제외하고 누락값은 추정하지 않는다. 사진은 전송하지 않는다. |
| 4. 완료 취소·오늘만 운동 대체 | 최근 세트/운동 완료 취소. 또는 대체 이름·세트 목표·휴식을 입력하고 오늘만 대체 적용 | 최근 완료 1회 취소를 지원한다. 후속 실제 기록 수동 편집은 이전 취소를 무효화하며 목표 세트가 바뀐 취소도 거부한다. 대체는 주간 기본 루틴과 이전 실제 기록을 보존한다. 성공 시 타이머 저장 상태와 런타임을 함께 정지한다. |
| 5. 실제 수행 기록으로 GPT 조정 | 원본 계획을 보기로 열기 → 현재 조건 확인 → 최근 7일/28일·어려웠던 점 입력 → 전송 미리보기 → 열린 계획을 수행 기록으로 조정 | 현재 조건과 원본 프로필·ID, 수행 기록을 함께 전송한다. 기록 없는 날짜는 실패로 추정하지 않고 미확인으로 표시한다. 결과와 변경 이유는 검토 가능한 새 추천으로 제공하며 실행 루틴에 자동 적용하지 않는다. |

실제 기록은 `session.actualSetsByExercise`, 저장 당시 운동 이름은 `session.exerciseNamesById`에 보관한다. 행 삭제 후에도 다른 세트 번호는 유지된다. 진행 중 계획은 `session.planSnapshot`, 적용 출처는 `sourcePlanId`, 최근 적용 복원 정보는 `routineChange`로 분리한다. JSON 전체 백업/복원에 이 정보가 포함된다.

저장 실패 시 변경 전 기록·루틴·요약으로 복구한다. 완료 취소와 당일 대체는 저장이 성공한 후에만 런타임 타이머를 정리한다. 다른 탭의 저장 변경 감지와 기존 저장 실패 안내를 계속 사용한다.

## 근거 코드

- `routine-planner.js`: `buildRoutine`, `preserveSessions`, `apply`, `restore` — 요일별 미리보기, 당일 계획 보존, 적용·복원 검증.
- `workout-journal.js`: `saveSet`, `deleteSet`, `previousSets`, `captureSet`, `undoLastCompletion`, `replaceToday` — 목표와 실제 분리, 세트 비교·수정, 완료 취소와 대체.
- `app.js`: `completeCurrentExercise`, `getCurrentPlan`, `syncSessionToCurrentPlan` 및 저장 정규화 — 기존 운동 실행·요약·저장 흐름 연결.
- `ai-coach.js`: `FitMindAdaptation.compareInbody`, `basePlan`, `performance`, `adaptationInput` — 날짜별 수치 비교, 원본 프로필·출처, 기간 기록과 미확인 날짜.
- `server/`: 기존 Codex OAuth 요청·입력 검증 경로를 확장하며 별도의 계정·API 키 저장 방식을 추가하지 않는다.

## 검증 범위

- `npm run check` 문법 검사 및 자동 테스트 **99개 통과, 실패·건너뜀 0개**. 적용·복원과 저장 실패, 실제 기록 입력·삭제·지난 기록 수정, 완료 취소·타이머 상태·후속 수정 보존, 당일 대체, 인바디 비교, 수행 기록 전송과 서버 입력 검증을 포함한다.
- 실제 브라우저: 합성 데이터를 사용한 데스크톱 및 너비 390px 화면에서 완료 취소·새로고침, 적용 시 진행 기록 보존·복원, 오늘만 대체, JSON 내보내기·복원을 확인했다. 이는 사용자 실제 건강 데이터나 실제 GPT 추천의 적합성 검증이 아니다.
- 화면 증거: `output/playwright/plan-apply-preview.png`, `output/playwright/workout-journal-mobile.png`. 실행 시나리오와 합성 백업: `output/playwright/workflow-smoke.js`, `output/playwright/workflow-backup.json`.
- 실제 Codex OAuth `gpt-5.6-luna` / `low` 조정 요청 1회가 HTTP 200으로 완료됐다. 합성 인바디 2개(28일 간격)·실제 입력 세트·원본 프로필의 전송을 확인했고, 사진 제외·결측값 null 보존·검증된 준비/유산소/총시간·변경 이유를 확인했다. 결과 보관 및 새로고침 후 모델·강도·선택 기록·기간·변경 이유가 유지됐다.
- 실제 GPT 결과를 수요일 루틴에 적용해 준비 3분·추천 운동·실제 세트 완료를 확인했다. 저장본을 다시 연 조정 미리보기에서 원본 ID와 수행 기록의 연결이 일치했으며, JSON 내보내기·복원·새로고침 후에도 진행 기록과 변경 이유가 유지됐다. 실제 서비스 호출은 합성 입력에 대한 기능 검증이며 추천의 의료적 적합성을 검증한 것은 아니다.
- 추가 화면 증거: `output/playwright/inbody-comparison-mobile.png`, `output/playwright/ai-adjustment-result.png`, `output/playwright/ai-workout-applied.png`. 재현 스크립트: `output/playwright/ai-live-smoke.js`(실행 시 실제 계정 요청 발생), `output/playwright/ai-apply-smoke.js`. 브라우저 콘솔 오류·경고 0개를 확인했다.
- 배포 경로: Vercel CLI 로그인 대신 기존 GitHub `main` → Vercel Production 자동 배포 연결을 확인했다. 공개 파일 6개만 `dist/`로 빌드하도록 설정했다. 이 문서 작성 시점에는 푸시 전이며, 배포 성공은 푸시한 커밋의 Vercel 상태와 공개 URL의 파일 일치 여부로 별도 확인한다.

최종 독립 검토에서 발견한 대체 전 운동의 집계 혼합, 저장 계획의 프로필 누락, 보관 전후 원본 ID 단절을 수정했다. 관련 20개 테스트와 별도 VM 경계 검증을 통과했으며 이 세 경로에서 남은 중요 결함은 발견되지 않았다.

## 운영 한계

운동 기록은 브라우저 LocalStorage에 저장되며 계정 간 자동 동기화가 없다. 중요한 기록은 전체 JSON 백업을 보관한다. 기존 주소와 로컬 주소의 저장 공간은 서로 다르다.

GPT 추천·조정은 `npm start`로 실행한 로컬 서버에서 기존 Codex OAuth 연결을 사용한다. 정적 Vercel 배포 또는 `file://`에서 로컬 OAuth를 직접 사용하지 않는다. 연결 계정의 모델 접근·사용량 제한이 적용되며 요청은 자동 재시도하지 않는다.

조정 요청에는 최대 최근 수행 기록 56개와 실제 세트 상세 80개를 포함하고 생략 수를 표시한다. 이력 없는 수치·실패·부상 상태를 만들어내지 않는다. 추천 검증은 구조·입력 제약 확인이며 의료적 적합성을 보증하지 않는다.
